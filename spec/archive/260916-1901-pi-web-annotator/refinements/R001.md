## Trigger and evidence

A live run on Brave 1.95.101 (Chromium 153.0.8010.37) opened the global side panel from the extension toolbar on an ordinary HTTP(S) page, but **Enable annotation on this page** failed with `No active page is available.` The frozen Current packet records the reproduction, source trace, official API evidence, alternatives, user confirmation, and lifecycle transition: [Attempt 2 in Current 02.01](../implementation/02-01-pi-bridge-integration.md#attempt-2---2026-09-16t190738z).

`browser-extension/service-worker.js` currently enables `openPanelOnActionClick`; the side panel later asks the worker to re-fetch the tab. The resulting tab has an ID but no URL/title because this browser-managed side-panel opening path did not grant `activeTab`. Chrome documents action invocation as an `activeTab` grant and documents programmatic `sidePanel.open()` as Chrome 116+ and user-gesture-bound:

- <https://developer.chrome.com/docs/extensions/develop/concepts/activeTab>
- <https://developer.chrome.com/docs/extensions/reference/api/sidePanel>

## Objective

Reconcile the canonical browser minimum and toolbar-action design so one explicit action invocation grants temporary access to the selected document, opens the global side panel, and preserves the least-privilege permission boundary.

## Affected contract

- Requirement 2's minimum changes from Chrome 114 to at least Chrome 116.
- Requirement 3 and acceptance must define how the toolbar action grants access, opens the global side panel, and relates to the separate **Enable** control.
- The narrow permission list remains `activeTab`, `scripting`, `sidePanel`, and `storage`, plus only the fixed loopback host permission.
- Browser documentation, manifest minimum, action lifecycle tests, and the real-browser checklist must be reconciled.
- Revised v1 browser support includes current Google Chrome/Chromium proper with a Chrome 116 API floor and Brave 1.95.101+ on macOS. Other Chromium derivatives remain unguaranteed.

## Confirmed facts and evidence

- **Fact:** `sidePanel.open()` is available from Chrome 116 and must be called in response to a user action. A `windowId` opens the existing global side panel.
- **Fact:** executing the extension action grants temporary `activeTab` access; the grant is lost on cross-origin navigation or tab close.
- **Fact:** automatic `openPanelOnActionClick` did not supply the needed grant in the live reproduction, matching the recorded Chromium extension-team behavior.
- **User decision:** enter formal same-item revision and evaluate Chrome 116+ with `chrome.action.onClicked` plus synchronous `chrome.sidePanel.open()`.
- **User decision:** preserve the narrow permission boundary rather than adding persistent HTTP(S) host access.
- **Fact:** the live reproduction used Brave, a Chromium derivative currently outside guaranteed v1 compatibility.

## Impact

- **Retained:** global side panel, explicit per-document access, standalone and bridge workflows, schema-v1 bundles, screenshot and privacy rules, session resilience, filesystem semantics, and path-based later intake.
- **Corrective:** action registration/opening, active-tab handoff, minimum browser version, mocks, documentation, and live test instructions.
- **Invalidated:** the claim that `openPanelOnActionClick` satisfies the required `activeTab` acquisition path; any passing test double that assumes URL/title access without simulating the action grant.
- **Pending:** implementation reconciliation, affected focused review, and real-browser reruns in both guaranteed browser families.

## Revised acceptance

- Clicking the extension action on a supported ordinary HTTP(S) page grants temporary access to that tab and opens the global side panel in the same user gesture.
- The panel does not inject automatically. The user must then choose **Enable annotation on this page** for that document.
- The implementation uses no persistent all-sites host access and fails clearly on restricted pages or unavailable API behavior.
- Every new tab and every document after access-revoking navigation requires a fresh qualifying toolbar action followed by the explicit Enable step.
- Automated tests reproduce the missing-tab-metadata failure path and prove the corrected action event, global panel opening, access lifecycle, and restricted-page handling.
- The affected real-browser scenarios pass in every browser promised by the revised support scope before T01/T02 completion evidence is reclaimed.

## Verification seams

- Manifest assertion for the revised minimum and unchanged permissions.
- Service-worker action-event test that supplies the real action tab, calls `sidePanel.open({ windowId })` synchronously, and does not use automatic `openPanelOnActionClick`.
- Regression test where a side-panel tab query lacks sensitive fields unless the action handoff occurred.
- Navigation, second-tab, restricted-page, and service-worker-replacement tests for grant metadata and explicit enablement.
