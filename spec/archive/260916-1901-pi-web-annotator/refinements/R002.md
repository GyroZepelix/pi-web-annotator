## Trigger and evidence

Live testing on Brave 1.95.101 (Chromium 153.0.8010.37) on macOS 26 Tahoe reached one accepted pending annotation, then disconnected **Finish and save...** failed with `This Chrome context does not provide the File System Access directory picker.` Pending state remained intact. The reproduction, screenshot, source trace, browser evidence, alternatives, user confirmation, and lifecycle transition are recorded in [Attempt 3 of Current 03.01](../implementation/03-01-active-tab-correction-and-integration-completion.md#attempt-3---2026-09-16t202901z).

The current source already feature-detects and directly calls `showDirectoryPicker({ mode: "readwrite" })` from the Finish click before any `await`. Brave disables the non-OPFS File System Access API by default and exposes it only behind `brave://flags/#file-system-access-api`:

- <https://github.com/brave/brave-browser/wiki/Deviations-from-Chromium-%28features-we-disable-or-remove%29>
- <https://github.com/brave/brave-browser/issues/29411>
- <https://developer.chrome.com/docs/capabilities/web-apis/file-system-access>
- <https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker>

## Confirmed facts and evidence

- **Fact:** `window.showDirectoryPicker` is absent in default Brave 1.95.101 in the tested side-panel context because Brave disables the underlying API by default.
- **Fact:** the current direct Finish click preserves transient user activation; changing call timing or adding a manifest permission cannot enable a browser-disabled Blink API.
- **Fact:** Brave users can opt in through an experimental browser-wide flag and relaunch, but this changes the promised operating environment and remains outside extension control.
- **Fact:** the authenticated `/annotate` bridge can already produce the same project-local schema-v1 bundle atomically without broadening extension permissions.
- **Fact:** download-based output cannot preserve arbitrary project-root selection, `.gitignore` handling, directory-atomic semantics, or the no-ZIP contract without a material output and permission redesign.
- **Fact:** `<input webkitdirectory>` provides readable file selection, not a writable directory handle.
- **User decision:** enter formal same-item revision and support default Brave as bridge-only while retaining standalone File System Access saving in Chrome/Chromium proper.

## Revised acceptance

- Chrome/Chromium proper retains standalone File System Access saving and project-aware bridge saving.
- Default Brave saves only through the authenticated `/annotate` bridge. When `showDirectoryPicker` is unavailable and the bridge is disconnected, Finish is disabled and persistent guidance tells the user to run `/annotate`.
- Missing or lost bridge state retains every pending annotation. Reconnection automatically restores Finish without requiring recapture.
- Capability detection, not browser-name sniffing, selects whether disconnected standalone saving is available. A Brave user who manually enables the experimental API may exercise the existing standalone path, but that configuration is not guaranteed acceptance scope.
- No browser path may claim success or clear state until the established bridge or File System Access validity rules pass.

## Verification seams

- Side-panel tests prove that missing `showDirectoryPicker` plus a disconnected bridge disables Finish and shows persistent `/annotate` guidance, while picker availability or authenticated bridge connection enables the supported path.
- Bridge-loss and reconnection tests prove state retention, disabled guidance, and automatic Finish recovery.
- Default Brave manual evidence covers action/Enable, draft retention, bridge save, bridge loss, reconnection, and later intake. Chrome/Chromium proper manual evidence additionally covers standalone File System Access behavior.
- Existing automated suite, package and Pi loader checks, focused review, and final whole-contract review after reconciliation.
